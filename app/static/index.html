REMOTE ACCESS GUIDE

SSH permissions & operations

Commands the dashboard runs on a registered host, and the access each one needs.

Commands run on the remote host

UNIT is a registered systemd service or socket; N is the requested log line count. User scope adds --user. Registration reads an existing unit; it never creates or starts one.

Check connection
/usr/bin/id
/usr/bin/systemctl --version
/usr/bin/journalctl --system --no-pager -n 1 -o short-iso
Read service state and start time
/usr/bin/systemctl show --no-pager --property=Id,Description,ActiveState,SubState,ActiveEnterTimestamp,FragmentPath,LoadState UNIT
/usr/bin/systemctl --user show --no-pager --property=Id,Description,ActiveState,SubState,ActiveEnterTimestamp,FragmentPath,LoadState UNIT

The first line is for System scope; the second is for User scope. Multiple units on one host can be queried together.

Open Status
/usr/bin/systemctl status --no-pager -n 35 UNIT
/usr/bin/systemctl --user status --no-pager -n 35 UNIT
Read recent and live logs
/usr/bin/journalctl -u UNIT -n N --no-pager -o short-iso
/usr/bin/journalctl -u UNIT -n N --no-pager -o short-iso --follow

User scope adds --user immediately after /usr/bin/journalctl. Live following keeps one SSH command running until paused or closed.

Start, Stop, Restart · User scope
/usr/bin/systemctl --user start UNIT
/usr/bin/systemctl --user stop UNIT
/usr/bin/systemctl --user restart UNIT
Start, Stop, Restart · System scope
/usr/bin/sudo -n /usr/bin/systemctl start UNIT
/usr/bin/sudo -n /usr/bin/systemctl stop UNIT
/usr/bin/sudo -n /usr/bin/systemctl restart UNIT

Open ports: The dashboard checks each assigned TCP Port from this host. Select one service or Port and enable Live to repeat only that check every 3 seconds. No socket scan or remote shell is used for Port checks.

Required permissions

SSH identity

Use a non-root account. Add this dashboard’s public key to that account’s ~/.ssh/authorized_keys; set ~/.ssh to mode 700 and authorized_keys to 600. Compare the server fingerprint through a trusted channel before selecting Trust host.

User services

The SSH account needs a working user manager and access to its own journal. An administrator can keep the manager running after logout:

sudo loginctl enable-linger USERNAME
System logs

Reading the system journal normally needs systemd-journal or adm membership; journal reads do not use sudo. An administrator can grant journal group access:

sudo usermod -aG systemd-journal USERNAME
System control

Allow only the required unit and actions through exact NOPASSWD sudo rules. The dashboard uses sudo -n and never asks for a password.

USERNAME ALL=(root) NOPASSWD: /usr/bin/systemctl start example.service, /usr/bin/systemctl stop example.service, /usr/bin/systemctl restart example.service

Edit with sudo visudo -f /etc/sudoers.d/host-dashboard and validate with sudo visudo -c. Replace USERNAME and example.service for each allowed unit. These setup commands are run by an administrator, not by the dashboard.

How the SSH session works

Each operation sends one fixed, noninteractive command over SSH. No PTY, stdin, password prompt or forwarding is used; strict host key checking stays on. OpenSSH can internally use the account’s shell with -c to run that command, but the dashboard does not open an interactive login shell or accept arbitrary command text.

Host-key scanning runs on the dashboard machine. The private key stays there. The website’s Open action opens a URL in your browser; it does not create an SSH tunnel. Services without a systemd unit have no remote status, controls or logs. Removing a dashboard entry does not stop its unit or remove the public key from the remote host.

Verify host identity

Compare this fingerprint with the server console or a trusted administrator. A network scan alone does not verify identity.

On the remote host: ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub (use the matching key type).
